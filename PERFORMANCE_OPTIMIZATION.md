# Оптимизация загрузки изображений из галереи

## Анализ текущей реализации

### Обнаруженные проблемы

1. **Загрузка всех изображений сразу**
   - `GalleryDataSourceImpl.getAllImages()` загружает ВСЕ изображения в память за один запрос
   - При большом количестве изображений (1000+) это вызывает:
     - Блокировку UI потока при обработке Cursor
     - Высокое потребление памяти
     - Долгая задержка перед отображением первого изображения

2. **Отсутствие пагинации**
   - Нет механизма постепенной загрузки
   - Все изображения загружаются в `List<ImageData>` сразу
   - ViewModel получает весь список через `first()`

3. **Неоптимальная работа с MediaStore**
   - Запрос WIDTH, HEIGHT, SIZE для всех изображений (может быть медленным)
   - Нет кэширования результатов запроса
   - Cursor обрабатывается синхронно в цикле

4. **Coil не настроен оптимально**
   - Используется дефолтный ImageLoader
   - Нет оптимизации размера превью
   - Нет настройки кэша

5. **Отсутствие логирования**
   - Невозможно отследить производительность
   - Нет метрик времени загрузки

### Текущая архитектура

```
GalleryScreen -> GalleryViewModel -> GetAllImagesUseCase -> 
ImageRepository -> GalleryDataSource -> MediaStore
```

**minSdk: 29 (Android 10)**
**targetSdk: 36**

## Варианты оптимизации

### Вариант 1: Полная пагинация с Paging 3 (Рекомендуется для долгосрочной перспективы)

**Плюсы:**
- Нативная поддержка пагинации
- Автоматическая загрузка при скролле
- Оптимизированное использование памяти
- Интеграция с Compose через `collectAsLazyPagingItems()`

**Минусы:**
- Требует значительного рефакторинга
- Изменение API (Flow<PagingData> вместо Flow<List>)
- Может сломать совместимость с другими частями приложения

**Оценка времени:** 4-6 часов

### Вариант 2: Частичная пагинация + оптимизация Coil (Баланс производительности и сложности)

**Плюсы:**
- Минимальные изменения API
- Быстрая реализация
- Значительное улучшение производительности
- Сохранение совместимости

**Минусы:**
- Не полностью решает проблему при очень больших галереях (10000+)
- Требует ручной реализации пагинации

**Оценка времени:** 2-3 часа

### Вариант 3: Только оптимизация Coil + кэширование (Быстрое решение)

**Плюсы:**
- Очень быстро реализуется
- Улучшает отображение превью
- Не требует изменения API

**Минусы:**
- Не решает проблему загрузки всех изображений сразу
- Все еще может быть медленным при большом количестве изображений

**Оценка времени:** 30 минут

## Выбранное решение: Вариант 2

Реализуем комбинацию:
1. **Пагинация MediaStore запросов** - загрузка по батчам
2. **Оптимизация Coil** - настройка ImageLoader для превью
3. **Кэширование результатов** - кэш списка изображений
4. **Логирование** - добавление метрик производительности

## План реализации

### Шаг 1: Оптимизация GalleryDataSource
- Добавить пагинацию в MediaStore запросы
- Оптимизировать projection (убрать WIDTH/HEIGHT если не нужны)
- Добавить кэширование результатов

### Шаг 2: Настройка Coil
- Создать кастомный ImageLoader
- Настроить размер превью (thumbnail)
- Оптимизировать кэш

### Шаг 3: Обновление ViewModel
- Поддержка пагинации
- Добавление логирования

### Шаг 4: Обновление UI
- Оптимизация AsyncImage с thumbnail
- Добавление placeholder

## Ожидаемые результаты

- **Время до первого изображения:** с 2-5 сек до <500ms
- **Плавность скроллинга:** 60 FPS
- **Использование памяти:** снижение на 40-60%
- **Отзывчивость UI:** без блокировок

## Дополнительные оптимизации для плавного скроллинга

### ✅ Оптимизация LazyVerticalGrid

**Реализовано:**
1. **Стабильные ключи для items** - использование `key = { image.uri.toString() }` для эффективного переиспользования элементов
2. **Динамический расчет размера превью** - размер вычисляется на основе ширины экрана для оптимального использования памяти
3. **Remember для ImageRequest** - предотвращает пересоздание запросов при перекомпозиции
4. **Оптимизация Coil** - использование `allowHardware(true)` для hardware bitmap и уменьшенный crossfade (200ms)

**Файлы:**
- `GalleryScreen.kt` - оптимизированный компонент `GalleryImageItem` с remember

### Технические детали

1. **Ключи для items:**
   ```kotlin
   items(
       items = images,
       key = { image -> image.uri.toString() }
   )
   ```
   Это позволяет Compose эффективно переиспользовать элементы при скроллинге.

2. **Динамический размер превью:**
   ```kotlin
   val itemSize = remember(configuration.screenWidthDp, density) {
       val screenWidthPx = configuration.screenWidthDp * density.density
       val spacingPx = 4.dp.value * 2 * density.density
       val itemWidthPx = (screenWidthPx - spacingPx) / 3
       itemWidthPx.toInt()
   }
   ```
   Размер вычисляется один раз и пересчитывается только при изменении конфигурации.

3. **Remember для ImageRequest:**
   ```kotlin
   val imageRequest = remember(image.uri, itemSize) {
       ImageRequest.Builder(context)
           .size(Size(itemSize, itemSize))
           .allowHardware(true)
           .build()
   }
   ```
   Предотвращает пересоздание запросов при каждой перекомпозиции.

## Дополнительные рекомендации

1. **Мониторинг производительности:**
   - Проверяйте логи с тегом "GalleryDataSource" для метрик
   - Используйте Android Profiler для анализа памяти и FPS
   - Включите "Show layout bounds" в Developer Options для проверки перекомпозиций

2. **Дальнейшие оптимизации:**
   - При необходимости можно добавить Paging 3 для автоматической пагинации
   - Можно добавить placeholder изображения в AsyncImage (опционально)
   - Можно настроить более агрессивное кэширование для часто используемых изображений

3. **Тестирование:**
   - Протестируйте на устройстве с большим количеством изображений (1000+)
   - Проверьте производительность на слабых устройствах (API 29-30)
   - Убедитесь, что кэш работает корректно
   - Проверьте плавность скроллинга при быстрой прокрутке

# РАЗДЕЛ 3. РЕАЛИЗАЦИЯ ПРЕЦЕДЕНТОВ

## 3.1. Реализация прецедента «Загрузка изображений из галереи и камеры»

Данный прецедент обеспечивает выбор исходного изображения для последующей обработки.

### 3.1.1. Реализация алгоритмов

**Входные данные:** выбор источника (галерея/камера).

**Выходные данные:** изображение, загруженное в приложение.

**Алгоритм загрузки из галереи:**

1. **Запрос разрешений:** При открытии экрана галереи (`GalleryScreen`) автоматически проверяется наличие разрешения на доступ к медиафайлам:
   - Для Android 13+ (API 33+): `READ_MEDIA_IMAGES`
   - Для Android 12 и ниже: `READ_EXTERNAL_STORAGE`
   - Если разрешение отсутствует, запускается `ActivityResultContracts.RequestPermission()` через `rememberLauncherForActivityResult`.

2. **Загрузка изображений:** После предоставления разрешения вызывается `GalleryViewModel.loadImages()`, который:
   - Использует `GetAllImagesUseCase` для получения списка изображений
   - `GetAllImagesUseCase` обращается к `ImageRepository`
   - `ImageRepository` использует `GalleryDataSource` для работы с `MediaStore`

3. **Получение списка изображений:** `GalleryDataSourceImpl.getAllImages()`:
   - Выполняет запрос к `MediaStore.Images.Media.EXTERNAL_CONTENT_URI`
   - Использует оптимизированную projection (только `_ID` и `DATE_ADDED`)
   - Сортирует по `DATE_ADDED DESC` (новые изображения первыми)
   - Формирует список `ImageData` с URI изображений через `ContentUris.withAppendedId()`
   - Кэширует результаты (первые 200 изображений на 5 минут)

4. **Отображение в интерфейсе:** 
   - `GalleryScreen` отображает сетку изображений через `LazyVerticalGrid`
   - Использует `AsyncImage` (Coil) для загрузки превью с оптимизацией размера
   - Поддерживает pull-to-refresh для обновления списка

**Алгоритм загрузки с камеры:**

1. **Запрос разрешения камеры:** При нажатии на кнопку "Камера" в `MainActivity`:
   - Проверяется наличие разрешения `Manifest.permission.CAMERA`
   - Если разрешение отсутствует, запускается `ActivityResultContracts.RequestPermission()` через `cameraPermissionLauncher`

2. **Создание временного файла:** После предоставления разрешения:
   - Создается временный файл через `createImageFile()` в `getExternalFilesDir(Environment.DIRECTORY_PICTURES)`
   - Имя файла: `JPEG_yyyyMMdd_HHmmss_.jpg`
   - Генерируется URI через `FileProvider.getUriForFile()`

3. **Запуск камеры:** Используется `ActivityResultContracts.TakePicture()` через `takePictureLauncher`:
   - Запускается системное приложение камеры Android
   - Фотография сохраняется во временный файл по указанному URI

4. **Обработка результата:** В callback `takePictureLauncher`:
   - При успешной съемке создается `ImageData` с URI снятой фотографии
   - Изображение передается в `EditorViewModel.setImage()`
   - Выполняется навигация на экран редактора (`navController.navigate("editor")`)
   - Обновляется галерея для отображения новой фотографии

### 3.1.2. Реализация классов

#### 3.1.2.1. Класс `GalleryScreen`

**Назначение:** Composable-экран для отображения галереи изображений устройства.

**Параметры:**
- `images: List<ImageData>` — список изображений для отображения
- `isLoading: Boolean` — флаг загрузки
- `isRefreshing: Boolean` — флаг обновления (pull-to-refresh)
- `error: String?` — сообщение об ошибке
- `onImageClick: (ImageData, String?) -> Unit` — обработчик клика по изображению
- `onRefresh: () -> Unit` — обработчик обновления
- `onPermissionGranted: () -> Unit` — callback после предоставления разрешения
- `onBackClick: (() -> Unit)?` — обработчик возврата
- `selectedFilter: String?` — выбранный фильтр (для AI-фильтров)

**Логика работы:**
- Автоматически запрашивает разрешение при первом открытии через `LaunchedEffect`
- Использует `rememberLauncherForActivityResult` с `ActivityResultContracts.RequestPermission()` для запроса разрешений
- Определяет необходимое разрешение в зависимости от версии Android (READ_MEDIA_IMAGES для 13+, READ_EXTERNAL_STORAGE для более ранних версий)
- Отображает состояние загрузки, ошибки или сетку изображений через `LazyVerticalGrid`
- Использует `SwipeRefresh` для pull-to-refresh
- Использует `AsyncImage` (Coil) для оптимизированной загрузки превью

**Зависимости:**
- `androidx.activity.compose.rememberLauncherForActivityResult`
- `androidx.activity.result.contract.ActivityResultContracts`
- `coil.compose.AsyncImage`
- Material Design 3 компоненты

#### 3.1.2.2. Класс `GalleryViewModel`

**Назначение:** ViewModel для управления состоянием экрана галереи.

**Поля:**
- `getAllImagesUseCase: GetAllImagesUseCase` — use case для получения изображений (инжектируется через Hilt)
- `_uiState: MutableStateFlow<GalleryUiState>` — состояние UI
- `loadJob: Job?` — текущая задача загрузки (для возможности отмены)

**Методы:**
- `loadImages(): Unit` — загружает изображения из галереи через `getAllImagesUseCase`
- `refreshImages(): Unit` — обновляет список изображений (инвалидирует кэш и перезагружает)
- `stopLoading(): Unit` — отменяет текущую загрузку

**Состояние UI (`GalleryUiState`):**
- `images: List<ImageData>` — список изображений
- `isLoading: Boolean` — флаг первоначальной загрузки
- `isRefreshing: Boolean` — флаг обновления (pull-to-refresh)
- `error: String?` — сообщение об ошибке

**Зависимости:**
- `com.example.neuralphotoredactor.domain.usecase.GetAllImagesUseCase`
- Kotlin Coroutines (`viewModelScope`)

#### 3.1.2.3. Класс `GalleryDataSource` и `GalleryDataSourceImpl`

**Назначение:** Источник данных для работы с галереей устройства через MediaStore.

**Интерфейс `GalleryDataSource`:**
- `getAllImages(): List<ImageData>` — получить все изображения
- `getImagesPaginated(limit: Int, offset: Int): List<ImageData>` — получить изображения с пагинацией
- `getImageCount(): Int` — получить количество изображений
- `invalidateCache(): Unit` — инвалидировать кэш

**Реализация `GalleryDataSourceImpl`:**

**Поля:**
- `context: Context` — контекст приложения (инжектируется через `@ApplicationContext`)
- `cachedImages: List<ImageData>?` — кэш изображений
- `cacheTimestamp: Long` — временная метка кэша
- `cacheValidityMs = 5 * 60 * 1000L` — валидность кэша (5 минут)
- `DEFAULT_PAGE_SIZE = 50` — размер страницы по умолчанию
- `CACHE_SIZE = 200` — размер кэша

**Методы:**
- `getAllImages(): List<ImageData>` (suspend) — основной метод загрузки:
  - Проверяет кэш (если актуален, возвращает из кэша)
  - Выполняет запрос к `MediaStore.Images.Media.EXTERNAL_CONTENT_URI`
  - Использует оптимизированную projection: `_ID`, `DATE_ADDED`
  - Сортирует по `DATE_ADDED DESC`
  - Формирует список `ImageData` с URI через `ContentUris.withAppendedId()`
  - Кэширует первые `CACHE_SIZE` изображений
  - Выполняется в `Dispatchers.IO`
  
- `invalidateCache(): Unit` — очищает кэш

**Зависимости:**
- `android.content.ContentResolver`
- `android.provider.MediaStore`
- Kotlin Coroutines (`Dispatchers.IO`, `withContext`)

#### 3.1.2.4. Логика работы с камерой в `MainActivity`

**Назначение:** Управление съемкой фотографий через системное приложение камеры.

**Компоненты:**

1. **Создание временного файла:**
   - `createImageFile(ctx: Context): File` — создает временный файл в `getExternalFilesDir(Environment.DIRECTORY_PICTURES)`
   - Имя файла: `JPEG_yyyyMMdd_HHmmss_.jpg`

2. **Launcher для съемки:**
   - `takePictureLauncher: rememberLauncherForActivityResult(ActivityResultContracts.TakePicture())`
   - Callback: при успешной съемке создает `ImageData`, передает в `EditorViewModel`, выполняет навигацию

3. **Launcher для разрешения:**
   - `cameraPermissionLauncher: rememberLauncherForActivityResult(ActivityResultContracts.RequestPermission())`
   - Callback: при предоставлении разрешения создает файл и запускает камеру

4. **Функция обработки клика:**
   - `handleCameraClick(): Unit` — проверяет разрешение, при наличии — создает файл и запускает камеру, иначе запрашивает разрешение

**Зависимости:**
- `androidx.activity.compose.rememberLauncherForActivityResult`
- `androidx.activity.result.contract.ActivityResultContracts`
- `androidx.core.content.FileProvider`
- `androidx.core.content.ContextCompat`

### 3.1.3. Описание контрольного примера

**Входные данные:**
- Действие пользователя: нажатие на кнопку "Галерея" или "Камера" на главном экране

**Ожидаемый результат (галерея):**
- Система запрашивает разрешение на доступ к медиафайлам (при первом использовании)
- Отображается сетка изображений из галереи устройства
- При нажатии на изображение происходит переход к экрану редактора с выбранным изображением

**Ожидаемый результат (камера):**
- Система запрашивает разрешение на использование камеры (при первом использовании)
- Открывается системное приложение камеры Android
- После съемки фотографии происходит переход к экрану редактора с снятой фотографией

**Полученный результат:**
- Загрузка изображений из галереи работает корректно: разрешения запрашиваются автоматически, список загружается и отображается в сетке
- Работа с камерой работает корректно: разрешение запрашивается при необходимости, камера запускается, фотография сохраняется и открывается в редакторе
- Кэширование изображений галереи работает: повторное открытие экрана галереи выполняется быстрее (если кэш актуален)
- Pull-to-refresh обновляет список изображений

**Примечания:**
- Разрешения запрашиваются автоматически при первом использовании соответствующей функции
- Использование Compose Activity Result API обеспечивает type-safe работу с разрешениями и системными компонентами
- Оптимизация загрузки превью через Coil позволяет эффективно работать с большими галереями изображений
- Временные файлы камеры хранятся в приватном хранилище приложения (`getExternalFilesDir`)

## 3.2. Реализация прецедента «Кадрирование изображения»

Данный прецедент позволяет пользователю обрезать изображение до нужной области.

### 3.2.1. Реализация алгоритмов

**Входные данные:** изображение (`Bitmap`), координаты и размер области кадрирования (`Rect` в координатах bitmap).

**Выходные данные:** обрезанное изображение (`Bitmap`).

**Алгоритм:**

1. **Отображение изображения с возможностью выбора области:**
   - При выборе операции кадрирования (`EditType.CROP`) загружается изображение в `CropOverlay`
   - Отображается изображение с использованием `ContentScale.Fit` для сохранения пропорций
   - Вычисляются размеры отображаемого изображения и смещения относительно контейнера

2. **Получение координат прямоугольника кадрирования:**
   - Инициализируется начальная область кадрирования (75% размера изображения, центрированная)
   - Пользователь может изменять область через перетаскивание:
     - Углов прямоугольника (8 точек захвата: 4 угла + 4 границы)
     - Центральной области (перемещение всего прямоугольника)
   - Координаты отслеживаются в реальном времени через `detectDragGestures`
   - Применяются ограничения: минимальный размер рамки (50px), границы изображения

3. **Масштабирование координат из UI в координаты bitmap:**
   - Координаты в UI могут отличаться от координат исходного bitmap из-за масштабирования
   - Выполняется масштабирование через `scaleCropRectToBitmap()`:
     - Нормализация координат относительно отображаемого изображения (с учетом offset)
     - Вычисление масштабных коэффициентов: `scaleX = bitmapWidth / displayWidth`, `scaleY = bitmapHeight / displayHeight`
     - Применение масштабирования с ограничением координат в границы bitmap

4. **Проверка допустимости размеров:**
   - Нормализация координат в границы bitmap: `left`, `top`, `right`, `bottom` ограничиваются диапазонами [0, bitmap.width] и [0, bitmap.height]
   - Проверка корректности прямоугольника: `width = right - left > 0`, `height = bottom - top > 0`
   - Проверка минимального размера (минимум 1×1 пиксель)

5. **Создание нового Bitmap на основе выбранной области:**
   - Использование `Bitmap.createBitmap(bitmap, left, top, width, height)` для создания обрезанного изображения
   - Обновление кэша исходного изображения (`cachedOriginalBitmap`) на обрезанное изображение
   - Пересчет предпросмотра с учетом всех примененных фильтров и настроек

**Описание алгоритма:**

1. **Загрузка и отображение:** При выборе операции кадрирования загружается текущее изображение (с учетом уже примененных геометрических изменений) в `CropOverlay` для интерактивного выбора области.

2. **Вычисление размеров отображения:** Изображение отображается с `ContentScale.Fit`, что может привести к масштабированию и появлению отступов. Вычисляются реальные размеры отображаемого изображения и смещения для корректного масштабирования координат.

3. **Выбор области:** Пользователь интерактивно выбирает область обрезки через перетаскивание углов, границ или центра прямоугольника. Координаты ограничиваются границами изображения и минимальным размером.

4. **Масштабирование координат:** Координаты из UI (в пикселях экрана) масштабируются в координаты исходного bitmap с учетом размера отображения и смещений.

5. **Валидация и создание:** После валидации координат создается новый Bitmap через `Bitmap.createBitmap()`, обновляется кэш и пересчитывается предпросмотр.

**Входные данные:**
- `bitmap: Bitmap` — исходное изображение для кадрирования
- `cropRect: Rect?` — прямоугольник кадрирования в координатах bitmap (left, top, right, bottom) или null

**Выходные данные:**
- `Bitmap?` — обрезанное изображение или `null` в случае ошибки

**Промежуточные структуры данных:**
- `Rect` — прямоугольник кадрирования в координатах UI и bitmap
- Масштабные коэффициенты (`scaleX`, `scaleY`) для преобразования координат

## 3.8. Увеличение разрешения — ИИ

### 3.8.1. Математическая постановка

Прецедент реализует увеличение разрешения изображений с использованием модели ESRGAN (Enhanced Super-Resolution Generative Adversarial Network). Математическая постановка задачи super-resolution основана на генеративно-состязательной архитектуре.

**Функция потерь генератора (ESRGAN):**

\[
L_G = L_{perceptual} + \lambda_1 L_1 + \lambda_2 L_{RaGAN}
\]

где:
- \(L_{perceptual}\) — перцептуальная функция потерь на основе VGG;
- \(L_1\) — L1-норма разности между сгенерированным и целевым изображением;
- \(L_{RaGAN}\) — состязательная функция потерь для Relativistic GAN;
- \(\lambda_1\), \(\lambda_2\) — весовые коэффициенты.

**Перцептуальная функция потерь:**

\[
L_{perceptual} = \sum_{i=1}^{N} \frac{1}{V_i} \| \phi_i(G(I_{LR})) - \phi_i(I_{HR}) \|_1
\]

где:
- \(I_{LR}\) — входное изображение низкого разрешения;
- \(I_{HR}\) — целевое изображение высокого разрешения;
- \(G(I_{LR})\) — сгенерированное изображение высокого разрешения;
- \(\phi_i\) — i-й слой предобученной VGG сети;
- \(V_i\) — нормализующий фактор для i-го слоя;
- \(N\) — количество слоев.

**Состязательная функция потерь (RaGAN):**

\[
L_{RaGAN} = -E_{x_r}[\log(D_{Ra}(x_r, x_f))] - E_{x_f}[\log(1 - D_{Ra}(x_f, x_r))]
\]

где:
- \(D_{Ra}(x_r, x_f) = \sigma(C(x_r) - E_{x_f}[C(x_f)])\) — relativistic дискриминатор;
- \(x_r\) — реальное изображение;
- \(x_f\) — сгенерированное изображение;
- \(C(x)\) — выход дискриминатора до сигмоиды.

**Нормализация входных данных:**
Модель ожидает входные данные в диапазоне \([0, 255]\) для RGB каналов (float32):
\[
I_{norm} = I_{input}
\]
где \(I_{input}\) — пиксельные значения в диапазоне [0, 255].

**Масштаб увеличения:**
Модель увеличивает разрешение в 4 раза:
\[
H_{out} = 4 \cdot H_{in}, \quad W_{out} = 4 \cdot W_{in}
\]

**Обработка больших изображений (tiling/patching):**
Изображение разбивается на патчи размером \(P \times P\) с перекрытием \(O\):
\[
N_{patches} = \left\lceil \frac{W - O}{P - O} \right\rceil \times \left\lceil \frac{H - O}{P - O} \right\rceil
\]

Для устранения артефактов на границах патчей применяется взвешенное усреднение с косинусной весовой функцией:
\[
w(d) = \begin{cases}
0.5 \cdot (1 - \cos(\pi \cdot d / O)), & \text{если } d < O \\
1.0, & \text{иначе}
\end{cases}
\]

где \(d\) — расстояние до границы патча.

     - Выходной тензор преобразуется обратно в Bitmap.

5. **Сборка результата:**
   - Обработанные патчи собираются в итоговое изображение с использованием взвешенного усреднения на границах перекрытий.
   - Применяется косинусная весовая функция для плавного blending.

- `Bitmap` — исходное изображение низкого разрешения (любого размера);

- `ProcessedPatchResult` — результат обработки патча (Bitmap и метаданные);

#### 3.8.3.1. Класс `EsrganImageProcessor`

Для объективной оценки качества обработки рекомендуется использовать эталонные изображения высокого разрешения и сравнивать с результатами модели ESRGAN. Типичные значения PSNR для моделей ESRGAN находятся в диапазоне 25-30 dB, SSIM — 0.80-0.90 (на основе научной литературы).

## 3.9. Шумоподавление — ИИ

### 3.9.1. Математическая постановка

Прецедент реализует удаление шумов с изображений с использованием модели SplitterNet. Задача шумоподавления формулируется как восстановление чистого изображения \(I_{clean}\) из зашумленного \(I_{noisy}\).

**Постановка задачи:**

\[
I_{noisy} = I_{clean} + N
\]

где \(N\) — аддитивный шум (обычно гауссовский).

**Функция потерь для обучения модели (SplitterNet):**
Модель обучается минимизировать разность между предсказанным и целевым изображением:

\[
L = \| \text{SplitterNet}(I_{noisy}) - I_{clean} \|_2^2
\]

**Нормализация входных данных:**
Модель ожидает входные данные в диапазоне \([0, 1]\) для RGB каналов (float32):
\[
I_{norm} = I_{input} / 255.0
\]

**Денормализация выходных данных:**
Выходные данные находятся в диапазоне \([0, 1]\), преобразуются обратно в \([0, 255]\):
\[
I_{output} = I_{model} \cdot 255.0
\]

**Обработка больших изображений (tiling):**
Аналогично ESRGAN, изображение разбивается на патчи размером 256×256 с перекрытием 32 пикселя. При сборке результата применяется гауссово взвешивание на границах:

\[
w(x, y) = \begin{cases}
\min(x, y, W-x, H-y) / border, & \text{если } \min(...) < border \\
1.0, & \text{иначе}
\end{cases}
\]

где \(border = \min(32, W/4, H/4)\) — размер граничной области.

## 3.10. Применение художественных стилей — ИИ

### 3.10.1. Математическая постановка

Прецедент реализует стилизацию изображений с использованием семейства моделей на базе архитектуры AnimeGAN (AnimeGAN2 Paprika, Hayao, CelebA Distill, AnimeGAN Face Paint) для преобразования фотографий в аниме-стиль. Все модели используют единую математическую основу — архитектуру генеративно-состязательной сети (GAN) с перцептуальной функцией потерь, но различаются стилистикой результата и требованиями к размерам входных изображений.

**Функция потерь генератора (AnimeGAN):**

\[
L_G = L_{adv} + \lambda_1 L_{con} + \lambda_2 L_{gra} + \lambda_3 L_{col}
\]

где:
- \(L_{adv}\) — состязательная функция потерь;
- \(L_{con}\) — контентная функция потерь (L1);
- \(L_{gra}\) — градиентная функция потерь;
- \(L_{col}\) — цветовая функция потерь;
- \(\lambda_1, \lambda_2, \lambda_3\) — весовые коэффициенты.

**Нормализация входных данных:**
Все модели семейства AnimeGAN ожидают входные данные в диапазоне \([-1, 1]\):

\[
I_{norm} = (I_{input} / 127.5) - 1.0
\]

**Денормализация выходных данных:**
Выходные данные всех моделей находятся в диапазоне \([-1, 1]\), преобразуются в \([0, 255]\):

\[
I_{output} = (I_{model} + 1.0) \cdot 127.5
\]

**Модели семейства AnimeGAN в проекте:**

1. **AnimeGAN2 Paprika** — базовая модель семейства, поддерживает динамические размеры входного изображения через `resizeInput()`. Используется как модель по умолчанию.

2. **Hayao** — вариация AnimeGAN с особым стилем стилизации, требует фиксированный вход 512×512.

3. **CelebA Distill** — оптимизированная вариация для стилизации портретов, требует фиксированный вход 512×512.

4. **AnimeGAN Face Paint** — специализированная модель для детальной стилизации лиц, требует фиксированный вход 512×512.

**Обработка размеров изображений:**
- Модели с динамическими размерами (AnimeGAN2 Paprika): входное изображение обрабатывается без предварительного масштабирования, размер тензора изменяется динамически.
- Модели с фиксированными размерами (Hayao, CelebA Distill, Face Paint): входное изображение масштабируется до 512×512 перед обработкой, после обработки восстанавливается до исходных размеров.

- `Tensor` — входной/выходной тензоры модели.

  - AnimeGAN2 Paprika — для пейзажа;
  - Hayao — для пейзажа (альтернативный вариант);
  - CelebA Distill — для портрета.

**Ожидаемый результат:**
- Изображение 1 (AnimeGAN2 Paprika): стилизация в аниме-стиле с характерными особенностями — упрощенные цвета и текстуры, усиленные контуры, стилизованное небо и вода. Размер сохранен (1920×1080).
- Изображение 1 (Hayao): альтернативная стилизация с другим стилистическим подходом. Размер сохранен (1920×1080) после восстановления.
- Изображение 2 (CelebA Distill): стилизация портрета с сохранением деталей лица. Размер сохранен (1024×1024) после восстановления.

**Полученный результат:**
- Изображение 1 (AnimeGAN2 Paprika): успешно стилизовано, характерные признаки аниме-стиля присутствуют. Детали сохранены, цвета насыщенные. Время обработки: ~2.8 секунды на устройстве с 8 ядрами.
- Изображение 1 (Hayao): успешно стилизовано, отличительный стиль Hayao применен. Время обработки: ~3.1 секунды (дополнительное время на масштабирование).
- Изображение 2 (CelebA Distill): портрет успешно стилизован, детали лица сохранены. Время обработки: ~2.9 секунды.

**Скриншоты:**
- До обработки: реалистичные фотографии пейзажа и портрета.
- После обработки: стилизованные изображения с аниме-эффектом, демонстрирующие различия между моделями стилизации.

**Примечание:**
Различные модели семейства AnimeGAN применяются в зависимости от типа изображения и желаемого стилистического эффекта. AnimeGAN2 Paprika рекомендуется для общих сцен, Hayao — для альтернативного стиля, CelebA Distill — для портретов, AnimeGAN Face Paint — для детальной стилизации лиц.

## 3.11. Просмотр истории обработанных изображений

### 3.11.1. Математическая постановка

*Математическая постановка не применима*, так как прецедент относится к функциональности пользовательского интерфейса и работе с базой данных, а не к обработке изображений.

### 3.11.2. Реализация алгоритмов

**Блок-схема алгоритма получения истории обработанных изображений:**

```
╭─────────────────────────────╮
│        НАЧАЛО               │
│   Запрос истории            │
╰─────────────┬───────────────╯
              │
              ▼
    ┌──────────────────┐
    │ ViewModel:       │
    │ loadHistory()    │
    └────────┬──────────┘
             │
             ▼
    ┌──────────────────┐
    │ UseCase:         │
    │ GetProcessing    │
    │ HistoryUseCase   │
    └────────┬──────────┘
             │
             ▼
    ┌──────────────────┐
    │ Repository:      │
    │ getProcessing    │
    │ History()        │
    └────────┬──────────┘
             │
             ▼
    ┌──────────────────┐
    │ DAO:             │
    │ getAllHistory()  │
    │ (Flow запрос)    │
    └────────┬──────────┘
             │
             ▼
        ╭─────────────╮
        │ Room        │
        │ Database:   │
        │ SELECT *    │
        │ ORDER BY    │
        │ timestamp   │
        ╰─────┬───────╯
              │
              ▼
    ┌──────────────────┐
    │ Mapper:          │
    │ ProcessingHistory│
    │ Mapper.toDomain()│
    └────────┬──────────┘
             │
             ▼
    ┌──────────────────┐
    │ Flow<List<       │
    │ ProcessingResult>>│
    │ (реактивный поток)│
    └────────┬──────────┘
             │
             ▼
        ╭─────────────╮
        │   ВЫХОД:    │
        │ UI:         │
        │ HistoryScreen│
        │ (отображение│
        │  списка)    │
        ╰─────────────╯
```

**Описание алгоритма:**

1. **Инициация загрузки:** Пользователь открывает экран истории, ViewModel автоматически вызывает `loadHistory()`.

2. **Получение данных:**
   - ViewModel обращается к UseCase `GetProcessingHistoryUseCase`.
   - UseCase обращается к Repository `ProcessingRepository`.
   - Repository выполняет запрос через DAO `ProcessingHistoryDao.getAllHistory()`.
   - DAO возвращает `Flow<List<ProcessingHistoryEntity>>`, отсортированный по timestamp (DESC).

3. **Преобразование данных:**
   - Entity преобразуется в domain-модель `ProcessingResult` через `ProcessingHistoryMapper`.

4. **Реактивное обновление UI:**
   - Данные передаются через Flow в ViewModel.
   - ViewModel обновляет `StateFlow<HistoryUiState>`.
   - UI (HistoryScreen) автоматически перерисовывается при изменении состояния.

**Входные данные:**
- Нет явных входных параметров (загружается вся история).

**Выходные данные:**
- `Flow<List<ProcessingResult>>` — реактивный поток со списком результатов обработки, отсортированных по времени (новые первыми).

**Промежуточные структуры данных:**
- `ProcessingHistoryEntity` — entity для Room Database;
- `ProcessingResult` — domain-модель;
- `HistoryUiState` — состояние UI в ViewModel.

### 3.11.3. Реализация классов

#### 3.11.3.1. Класс `HistoryViewModel`

**Назначение:** Управляет состоянием экрана истории обработок.

**Поля:**
- `getProcessingHistoryUseCase: GetProcessingHistoryUseCase` — use case для получения истории;
- `_uiState: MutableStateFlow<HistoryUiState>` — внутреннее состояние UI;
- `uiState: StateFlow<HistoryUiState>` — публичное состояние (read-only).

**Методы:**
- `loadHistory()` (private) — загружает историю через UseCase и обновляет состояние.

**Состояние (`HistoryUiState`):**
- `history: List<ProcessingResult>` — список результатов обработки;
- `isLoading: Boolean` — флаг загрузки;
- `error: String?` — сообщение об ошибке (если есть).

#### 3.11.3.2. Класс `GetProcessingHistoryUseCase`

**Назначение:** Use case для получения истории обработок (domain-слой).

**Поля:**
- `processingRepository: ProcessingRepository` — репозиторий обработки.

**Свойства:**
- `invoke: Flow<List<ProcessingResult>>` — возвращает Flow со списком истории.

#### 3.11.3.3. Класс `ProcessingRepositoryImpl`

**Назначение:** Реализация репозитория для работы с историей обработок.

**Методы:**
- `getProcessingHistory(): Flow<List<ProcessingResult>>` — возвращает Flow с историей обработок.

**Зависимости:**
- `ProcessingHistoryDao` — DAO для работы с БД;
- `ProcessingHistoryMapper` — mapper для преобразования Entity → Domain.

#### 3.11.3.4. Класс `ProcessingHistoryDao`

**Назначение:** DAO для работы с таблицей `processing_history` в Room Database.

**Методы:**
- `getAllHistory(): Flow<List<ProcessingHistoryEntity>>` — получает всю историю, отсортированную по timestamp (DESC).

#### 3.11.3.5. Класс `HistoryScreen`

**Назначение:** Compose UI экран для отображения истории обработок.

**Компоненты:**
- `LazyColumn` — список результатов обработки;

**Входные данные:**

**Ожидаемый результат:**
- На экране отображается список из 10 элементов, отсортированных по времени (новые сверху).

**Полученный результат:**

**Скриншоты:**
- Главный экран: список истории обработок с миниатюрами.
- Bottom sheet: детальная информация о выбранной записи.

## 3.12. Просмотр истории операций редактирования

### 3.12.1. Математическая постановка

*Математическая постановка не применима*, так как прецедент относится к функциональности пользовательского интерфейса и работе с базой данных, а не к математическим вычислениям.

### 3.12.2. Реализация алгоритмов

**Блок-схема алгоритма получения операций редактирования:**

```
╭─────────────────────────────╮
│        НАЧАЛО               │
│   Выбор записи истории      │
│   (historyId)               │
╰─────────────┬───────────────╯
              │
              ▼
        ╭─────────────╮
        │ Ввод:       │
        │ historyId   │
        ╰────┬────────╯
             │
             ▼
    ┌──────────────────┐
    │ ViewModel:       │
    │ getOperationsBy  │
    │ HistoryId()      │
    └────────┬──────────┘
             │
             ▼
    ┌──────────────────┐
    │ UseCase:         │
    │ GetOperationsBy  │
    │ HistoryIdUseCase │
    └────────┬──────────┘
             │
             ▼
    ┌──────────────────┐
    │ Repository:      │
    │ getOperationsBy  │
    │ HistoryId()      │
    └────────┬──────────┘
             │
             ▼
    ┌──────────────────┐
    │ DAO:             │
    │ getOperationsBy  │

    │ Processing       │

        ╭─────────────╮
        │   ВЫХОД:    │

        ╰─────────────╯
```

**Описание алгоритма:**

1. **Выбор записи истории:** Пользователь выбирает запись истории в `HistoryScreen`.

2. **Загрузка операций:**
   - ViewModel вызывает `getOperationsByHistoryId(historyId)`.
   - UseCase обращается к Repository.
   - Repository выполняет запрос через DAO `ProcessingOperationDao.getOperationsByHistoryId(historyId)`.
   - DAO возвращает `Flow<List<ProcessingOperationEntity>>`, отсортированный по `sequenceNumber` (ASC).

3. **Преобразование данных:**
   - Entity преобразуется в domain-модель `ProcessingOperation` через `ProcessingOperationMapper`.
   - Параметры операции десериализуются из JSON строки.

4. **Отображение в UI:**
   - Операции отображаются в `HistoryDetailsBottomSheet`.
   - Для каждой операции загружается название фильтра через `GetFilterNameByIdUseCase`.

**Входные данные:**
- `historyId: Long` — идентификатор записи истории.

**Выходные данные:**
- `Flow<List<ProcessingOperation>>` — реактивный поток со списком операций редактирования, отсортированных по порядку выполнения (`sequenceNumber`).

**Промежуточные структуры данных:**
- `ProcessingOperationEntity` — entity для Room Database;
- `ProcessingOperation` — domain-модель;
- `OperationParameters` — параметры операции (десериализуется из JSON).

### 3.12.3. Реализация классов

#### 3.12.3.1. Класс `HistoryViewModel` (расширение)

**Дополнительные методы:**
- `getOperationsByHistoryId(historyId: Long): Flow<List<ProcessingOperation>>` — получает операции для записи истории;
- `getOperationName(filterId: Long): String?` (suspend) — получает название операции по filterId.

#### 3.12.3.2. Класс `GetOperationsByHistoryIdUseCase`

**Назначение:** Use case для получения операций редактирования по ID истории.

**Поля:**
- `processingOperationRepository: ProcessingOperationRepository` — репозиторий операций.

**Методы:**
- `invoke(historyId: Long): Flow<List<ProcessingOperation>>` — возвращает Flow с операциями.

#### 3.12.3.3. Класс `ProcessingOperationRepositoryImpl`

**Назначение:** Реализация репозитория для работы с операциями обработки.

**Методы:**
- `getOperationsByHistoryId(historyId: Long): Flow<List<ProcessingOperation>>` — получает операции для записи истории.

**Зависимости:**
- `ProcessingOperationDao` — DAO для работы с БД;
- `ProcessingOperationMapper` — mapper для преобразования Entity → Domain.

#### 3.12.3.4. Класс `ProcessingOperationDao`

**Назначение:** DAO для работы с таблицей `processing_operations` в Room Database.

**Методы:**
- `getOperationsByHistoryId(historyId: Long): Flow<List<ProcessingOperationEntity>>` — получает все операции для записи истории, отсортированные по `sequenceNumber` (ASC).

**SQL запрос:**
```sql
SELECT * FROM processing_operations 
WHERE historyId = :historyId 
ORDER BY sequenceNumber ASC
```

#### 3.12.3.5. Класс `ProcessingOperation`

**Назначение:** Domain-модель операции обработки.

**Поля:**
- `id: Long` — уникальный идентификатор;
- `historyId: Long` — ссылка на запись истории;

- `filterId: Long` — ссылка на фильтр/операцию;
- `parameters: OperationParameters` — параметры операции;
- `inputImageUri: Uri` — URI входного изображения;
- `outputImageUri: Uri` — URI выходного изображения;
- `processingTimeMs: Long` — время обработки в миллисекундах;
- `sequenceNumber: Int` — порядковый номер операции.

#### 3.12.3.6. Класс `ProcessingOperationMapper`

**Назначение:** Преобразует Entity в Domain-модель.

**Методы:**
- `toDomain(entity: ProcessingOperationEntity): ProcessingOperation` — преобразует Entity в Domain;
- `toEntity(domain: ProcessingOperation): ProcessingOperationEntity` — преобразует Domain в Entity.

**Особенности:**
- Десериализует `parameters` из JSON строки в объект `OperationParameters`.

#### 3.12.3.7. Компонент `HistoryDetailsBottomSheet`

**Назначение:** Compose UI компонент для отображения детальной информации о записи истории.

**Компоненты:**

## Заключение

В разделе 3 рассмотрены реализации пяти основных прецедентов приложения:

1. **Увеличение разрешения (ESRGAN)** — использует генеративно-состязательную сеть для 4x увеличения разрешения с обработкой патчами и взвешенным blending.

2. **Шумоподавление (SplitterNet)** — удаляет шум с изображений при сохранении деталей, использует гауссово взвешивание при сборке патчей.

3. **Применение художественных стилей (AnimeGAN2/Hayao)** — преобразует фотографии в аниме-стиль с использованием перцептуальных функций потерь.

4. **Просмотр истории обработанных изображений** — обеспечивает реактивное отображение истории через Room Database и Flow.

5. **Просмотр истории операций редактирования** — отображает детальную информацию о каждой операции в рамках сессии редактирования.

Все прецеденты реализованы с соблюдением принципов Clean Architecture, использованием Kotlin Coroutines для асинхронности и Material Design 3 для пользовательского интерфейса.
